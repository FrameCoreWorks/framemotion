# Photoreal three.js blocks

Photographic image quality for any three.js engine, rendered in the browser on the same seekable clock as type and boards. Adapted from Leonxlnx/room-at-dawn (MIT, Leon Lin) and rewritten on the FrameMotion engine kit; each file's header names the source (see `integrations/room-at-dawn/`). Packs 1 (lens, accumulation, grade) and 5 (baked light) of the photoreal engine; the material library and props come later (see the own-engines plan).

| Block | What it does |
| --- | --- |
| `lens.mjs` | `subframePlan(frame, {fps, samples, shutter, aperture})`: n sub-frames per frame, each with a time inside the open shutter (stratified), a pixel jitter (Halton 2, 3) and a point on a round aperture (Halton 5, 7). `shearProjection(m, ...)` shifts the image by the jitter and keeps the focus plane still while the camera crosses the aperture. |
| `accum-camera.mjs` | `createAccumCamera({THREE, renderer, width, height}).render({scene, camera, frame, fps, samples, shutter, aperture, focus, prepare})`: averages the sub-frames into one linear HDR target. That one loop gives anti-aliasing, thin-lens depth of field and a real shutter (motion blur). `prepare(t)` is the engine's seek; the scene is left at the frame time. Sums are 32-bit float where the GPU can blend them (`precision` says which): 96 sub-frames of one grey average back within 0.04%, against 0.8% with half floats (measured in SwiftShader). Works from a parented or scaled camera and restores the renderer even when a sub-frame fails. |
| `film-grade.mjs` | `createFilmGrade({THREE, renderer, width, height}).render(hdr, look, {seed, target})`: bloom from a mip pyramid, exposure and white balance, vignette before the curve, tint by tonal range, saturation, contrast around mid grey, Uchimura's filmic curve, very bright light rolled towards white (`highlightRolloff`), grain weaker in the highlights and a dither. Input above 60 is clamped first so one hot pixel cannot flood the bloom; the bloom is normalised by its number of levels. Grain is seeded by the frame through a small offset. `gradePixel()` is the same grade in JavaScript; a test holds the shader to it within one 8-bit step. |
| `bake.mjs` | Baked light per vertex. `collectScene(THREE, root)` welds the lit meshes' vertices into points; `createTracer(...)` path-traces the diffuse light arriving at each point (E/π) and its main direction, over a three-mesh-bvh BVH: sky gradient, a sun disc, area lights (`rects`) and window `portals` sampled directly (portals weighted against cosine sampling, so a room lit only through a window converges fast), Russian roulette from the second bounce. Each point has its own seeded random stream, so the result is the same however the work is split. `smoothResult()` smooths along the mesh, not across creases. `bakeHere()` does it all in one thread. A mesh or material with `userData.gi = false` gets no baked light; `userData.occluder = false` lets light through. |
| `bake-node.mjs` | The bake in Node on worker threads: `node photoreal/bake-node.mjs --scene <module> --out <file.gi.bin> [--spp 256] [--seed 1] [--workers N] [--smooth 2]`. The scene module exports `bakeSetup(THREE) -> {root, lights}` with the same mesh names the page builds. |
| `gi-file.mjs` | The `.gi.bin` file: half floats per vertex, keyed by the mesh's name path and vertex count. `packBake` / `readBake`. |
| `gi-material.mjs` | `createGi(THREE)`: `apply(root, buffer)` patches each lit MeshStandard/MeshPhysical material (its maps, roughness, metalness and real-time lights stay) to add the baked light, shaded through the normal map by the baked direction, drops the environment's diffuse part (the bake holds it) and box-projects reflections onto the room; it returns `{applied, stale}`, where `stale` names meshes whose geometry no longer matches the file. `captureEnv(renderer, scene, {position, boxMin, boxMax})` renders the reflection probe once. The patch throws when three.js changed the shader code it edits. |
| `room/` | Our own test scene for the bake (the Motion project's test scene was not available): a room lit only through a window by a low sun and the sky, with an oak table, a steel plate, a clearcoat sphere and a cube; the direct sun is a real-time light with a shadow map, the sky and every bounce are baked (`room.gi.bin`, 13,272 points). Registered as `photoreal-room`. Rebake after changing the scene: `node photoreal/bake-node.mjs --scene photoreal/room/scene.mjs --out photoreal/room/room.gi.bin --spp 1024 --smooth 3`. |
| `demo/` | A steel plate, a glossy sphere and a small cube on a table in warm low light: a push-in, then a hold. Registered as `photoreal-demo`. |

## Settings that matter

- `samples`: 16 for a preview, 32 to 64 for delivery, up to 96 for shallow focus. Time grows linearly with samples.
- `aperture` (metres, lens radius): 0 is a pinhole (everything sharp); 0.005 to 0.02 is product photography; focus is the distance to the subject along the view axis.
- `shutter`: 0.5 is a 180° shutter; 0 freezes motion.
- `look`: start from `DEFAULT_LOOK`; keep `grain` at or below 0.02 for social video (compression eats more).

## Limits

- Baked light suits a still or slowly changing set: it is per vertex, so a surface needs enough vertices (subdivide large planes; the room's floor is 64×64), and anything that moves a lot (a person, a car) keeps real-time light. A light that changes during the shot needs a real-time light for its direct part (`sun.direct: 'realtime'`), as in the room.
- A mesh renamed or remeshed after the bake comes back in `stale` and gets flat light; rebake. The file also records a hash of the scene's geometry, materials and light points (`meta.scene`), which a test compares with the room scene.
- What the bake leaves out (the bake log names each case under `[bake] note:`): an InstancedMesh gets no baked light and casts no shadow in the bake; a mesh with several materials is baked and patched with its first one only; the bounce colour of a textured material comes from `material.color` unless you set `material.userData.albedo`; light is gathered on the front side only, so a thin two-sided object (a leaf, a sheet) blocks light without passing any through; each path's contribution is capped at 30, which darkens points right next to a very strong lamp a little.
- A shader the patch breaks (three.js renamed a variable it uses) would only log a compile error and draw nothing: call `gi.guard(renderer)` before the first render, as the room does (`apply()` does not do it for you), so the page stops with an error instead; three.js checks a program when it is first used, so the error comes at the latest on the first frame.
- The demo is a technical test scene, not a style; a film takes its look from the brief.
- Baking the room: about 60 s at 256 samples on 4 cloud CPU threads, about 7 min at 1024 samples (the shipped file, smoothing 3) on 3 busy threads (2026-11-16); rendering it: about 5 s per frame at 540×960 and 16 samples in SwiftShader. Graphics card, Mac and image quality on real hardware: NOT_RUN.
- Measured on 2026-11-14 in a cloud container with software WebGL (SwiftShader): 540×960, 32 samples, about 3.5 s per frame. These blocks on a graphics card: not measured yet (NOT_RUN). For scale, the FCWM prototype of the same technique (not this code) rendered 1080×1920 with 96 sub-frames at about 0.30 s per frame on a Mac mini M4 (report of 2026-11-14).
